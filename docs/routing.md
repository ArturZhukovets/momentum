# Как работает роутинг в Momentum (простыми словами)

## Кнопка — это не всегда callback

В боте есть два вида кнопок, и они работают совершенно по-разному.

**Inline-кнопки** (прикреплены к конкретному сообщению, например `CANCEL_BUTTON` в
[keyboards/common.py](../src/momentum/keyboards/common.py)) при нажатии шлют Telegram'у
структурированный `callback_data` — как раз то, что описано типизированными фабриками в
[keyboards/callbacks.py](../src/momentum/keyboards/callbacks.py) (`ActionCB`, `KindCB`,
`SkipCB` и т.д.). Хендлеры ловят их через `@router.callback_query(...)`.

**Reply-кнопки** (постоянная клавиатура снизу экрана — `main_menu()` в
[keyboards/common.py](../src/momentum/keyboards/common.py): "➕ Добавить тренировку",
"📜 История" и так далее) при нажатии **просто отправляют обычное текстовое сообщение** с
текстом кнопки. Для Telegram и для aiogram это неотличимо от того, если бы пользователь
своими руками напечатал "📜 История" и отправил. Именно поэтому в `callbacks.py` для них
ничего нет — там только `CallbackData` для inline-кнопок, у reply-кнопок никакого payload
не существует.

Хендлеры ловят такие сообщения обычным текстовым фильтром:

```python
@router.message(F.text == texts_common.BTN_HISTORY)
```

## Хендлер = чек-лист условий

Каждый хендлер — это функция плюс набор фильтров-условий, навешанных декоратором.
**Все условия одного хендлера обязаны совпасть одновременно** (это `AND`, а не приоритет
одного условия над другим):

```python
@router.message(Measure.weight, F.text)
async def got_measure_weight(...):
    ...
```

Чек-лист этого хендлера:

1. Апдейт — текстовое сообщение.
2. Текущий FSM-стейт пользователя равен `Measure.weight`.
3. В сообщении есть текст.

`Measure.weight` тут — не что-то особенное, это просто `StateFilter(Measure.weight)`,
записанный сокращённо. Он проверяется наравне с `F.text`, а не "сначала" или "в
приоритете".

## Порядок проверки: роутеры, потом хендлеры внутри них

aiogram не ищет "самый подходящий" хендлер по всему приложению — он идёт **строго по
порядку** и останавливается на первом, чей чек-лист сошёлся целиком:

1. Роутеры проверяются в том порядке, в котором они добавлены через `include_router()` в
   [app.py](../src/momentum/app.py#L47).
2. Внутри одного роутера хендлеры проверяются в порядке объявления сверху вниз по файлу.
3. Как только чек-лист хендлера сошёлся — он выполняется, и поиск останавливается. Дальше
   по цепочке апдейт не идёт.
4. Если ни один хендлер нигде не подошёл — апдейт молча игнорируется, бот не отвечает.

Текущий порядок роутеров в Momentum:

```text
common → admin → admin.denied → add_workout → onboarding → profile_handlers
       → goal → measure → profile_common_handlers → history → reports → suggestions
```

Порядок — не случайный, местами он специально важен (см. комментарии в
[app.py:54](../src/momentum/app.py#L54) и [app.py:62](../src/momentum/app.py#L62)), но
он же — источник неочевидных эффектов ниже.

## Три базовых случая

### 1. Обычный текст, без стейта и без команды

Стейт пустой (`None`), пользователь просто что-то написал. Подходят только хендлеры, у
которых **нет** `StateFilter` (или он явно требует `None`) и совпадает текстовый фильтр.
Если нигде не совпало — тишина, ответа не будет.

### 2. Команда

`/profile` — это тоже просто *текст*, начинающийся с `/`. Фильтр `Command("profile")`
проверяет именно префикс и **вообще не смотрит на стейт**:

```python
@router.message(Command("profile"))
async def cmd_profile(...):
```

Это значит, что `/profile` в теории должен срабатывать всегда, независимо от текущего
шага в любом другом флоу. Но это только в теории — см. пример-ловушку ниже.

### 3. Текст + стейт вместе

Комбинация из двух условий в одном хендлере, например `got_measure_weight` выше или:

```python
@router.message(StateFilter(AddWorkout.cardio_description, AddWorkout.strength_description), F.text)
async def got_description(...):
```

Оба условия обязательны. Если стейт не тот — не сработает, даже если текст в порядке.
Если стейт тот, но апдейт не текстовый (например, стикер) — тоже не сработает, тогда в
дело обычно вступает соседний fallback-хендлер без `F.text`, который ловит "что угодно" в
этом стейте и просит переслать текст.

## Ловушка: широкие фильтры перехватывают всё раньше, чем кажется

Самое неочевидное: хендлер с фильтром "такой-то стейт + `F.text`" не различает, что
именно за текст пришёл. Кнопка меню, команда, случайное слово — для него всё "текст",
значит всё подходит под чек-лист.

**Пример 1.** Пользователь в процессе `/measure`, стейт — `Measure.weight`
([handlers/measure.py](../src/momentum/handlers/measure.py)). Он жмёт кнопку
"📜 История". Роутер `measure` (позиция 61 в `app.py`) стоит раньше роутера `history`
(позиция 65). Дойдя до `measure.router`, диспетчер натыкается на
`got_measure_weight(Measure.weight, F.text)` — а текст "📜 История" полностью
удовлетворяет условию "есть текст". Хендлер срабатывает, пытается распарсить это как
число веса, не получается — пользователь видит ошибку валидации вместо истории.
До `history.router` дело просто не доходит.

**Пример 2.** Тот же принцип работает и в обратную сторону здесь же: кнопка
"➕ Добавить тренировку" **срабатывает нормально**, потому что роутер `add_workout`
(позиция 57) стоит раньше `measure` (позиция 61) — диспетчер найдёт её entry-хендлер ещё
до того, как доберётся до `measure.router` с его широким фильтром.

**Пример 3.** Даже команда не защищена. Если пользователь посреди ввода описания
тренировки (`AddWorkout.cardio_description`) наберёт `/profile`, диспетчер сначала
встретит `got_description(StateFilter(...), F.text)` в `add_workout.router` (позиция 57,
раньше `profile_handlers` на позиции 59) — а `/profile` тоже "просто текст". Строка
`/profile` буквально попадёт в поле описания тренировки, а `Command("profile")` в
`profile.py` даже не будет проверен.

## Итоговое правило

Кнопка или команда без `StateFilter` **гарантированно** прерывает текущий флоу только
если её роутер зарегистрирован в `app.py` **раньше**, чем роутер, которому принадлежит
текущий стейт. Если её роутер зарегистрирован позже — она рискует быть проглоченной
локальным широким fallback-хендлером (`StateFilter(...) + F.text` без проверки
конкретного содержимого) активного сейчас флоу.

Официальный, гарантированно рабочий способ выйти из любого флоу — inline-кнопка
"✖️ Отмена" (`ActionCB(name="cancel")`, обрабатывается централизованно в
`handlers/common.py`) или команда `/cancel`: оба чистят стейт (`state.clear()`) и не
зависят от порядка роутеров.

## Практический вывод для новых флоу

Если добавляете новый FSM-флоу с широким fallback-хендлером вида
`@router.message(SomeState, F.text)`:

1. Помните, что он перехватит **любой** текст в этом стейте — включая кнопки меню и
   команды, если их роутер зарегистрирован позже вашего.
2. Не полагайтесь на то, что пользователь "просто нажмёт другую кнопку" и выйдет из
   вашего флоу — скорее всего не выйдет.
3. Единственный надёжный выход из любого стейта — явный `state.clear()`, вызванный либо
   Cancel-хендлером, либо entry-хендлером, чей роутер зарегистрирован раньше вашего в
   `app.py`.
