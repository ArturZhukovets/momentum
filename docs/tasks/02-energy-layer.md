# Переведи цель в калории: расход тренировок и ориентир по питанию

## WHAT

> Добавить длительность и интенсивность **всем** типам тренировок, посчитать расход за тренировки по MET, базовый обмен по Миффлину-Сан Жеору, и показать в недельном/месячном отчёте ориентир: сколько калорий в день нужно при текущем темпе цели. Только факт, без советов и без «подкрутить».

Делается **сразу после** `01-goal-pace.md`: нужна колонка `target_rate_kg_per_month`. От `services/pace.py` эта задача технически не зависит — фактический темп здесь не используется.

## WHY

Цель в килограммах — это результат, на который нельзя нажать. «Минус 2 кг в месяц» не подсказывает, что делать сегодня вечером. Калории — это та величина, которой человек управляет каждый день, и все данные для перевода у нас уже есть: пол, возраст, рост из `user_profiles`, актуальный вес из `body_measurements`, тренировки с длительностью и усилием из `workouts`, скорость из цели.

Плюс второй эффект, который важен сам по себе: бот показывает **две ручки** вместо одной — можно меньше есть, а можно больше двигаться. Расход от тренировок мы считаем из реальных записей, поэтому вторая ручка честная, а не декоративная.

## Вердикт

Относится к боту: да.
Уже реализовано: нет. Ни калорий, ни MET, ни BMR в проекте нет; `services/` содержит `periods`, `stats`, `measurements`, `workout_types`, `reports` (+ `pace` после предыдущей задачи).
Реализуемо: да, новых зависимостей не нужно — обе формулы арифметические. Два реальных препятствия, оба решаются внутри задачи: у `gym` и `home_workout` сейчас нет `duration_min`/`effort` (T-1), а `WorkoutStatRow` — слишком узкая проекция (T-3).

## Принятые решения

Зафиксированы в обсуждении до начала работы, менять в ходе реализации не надо:

- длительность и интенсивность спрашиваются у **всех** типов — единый формат заполнения, а не только ради калорий;
- **никакой калибровки по факту изменения веса.** Мы не трекаем еду, поэтому приписать расхождение плана и факта расходу (или питанию) нельзя — это было бы выдумыванием причины. Бот показывает расчёт и не делает выводов;
- **никаких советов и предложений** «подкрутить темп», «добавить тренировку». Только числа и что они значат;
- числа округляются до полусотни, формулировки несут «примерно» и «по записанным тренировкам» как факт, а не как вежливость: и MET, и Миффлин дают разброс в пару сотен калорий;
- единственное исключение из «только факт» — безопасный порог (T-5).

## План

### T-1 — Длительность и интенсивность всем типам

В `services/workout_types.py`, `_FIELDS_BY_TYPE`:

```python
"gym":          (BODY_PARTS_FIELD, DURATION, EFFORT, DESCRIPTION),
"home_workout": (BODY_PARTS_FIELD, DURATION, EFFORT, DESCRIPTION),
```

Правка только в каталоге: FSM добавления тренировки генерик и ходит по `fields_for(type)`, так что хендлеры и клавиатуры не трогаются. `DURATION` и `EFFORT` уже объявлены в этом же модуле, тексты вопросов (`duration_min`, `effort`) уже есть в `texts/workout.py`.

Последствия, которые надо учесть дальше по коду:

- оба поля скипаемые, как всё остальное, поэтому `None` обрабатывается всегда — даже для новых записей;
- **старые строки останутся с `NULL`** и в сумму расхода не попадут. Это не баг, но формулировка в отчёте должна быть «по записанным тренировкам», а не притворяться полной суммой;
- бонус, ради которого это стоит делать даже без калорий: «минут за неделю» и «минут по типам» станут осмысленными — сейчас их посчитать нельзя, потому что половина тренировок без длительности.

Проверить, что карточка тренировки (`formatters/workout.py`) корректно печатает новые поля у `gym`/`home_workout`.

### T-2 — `services/energy.py`: чистый модуль расчётов

Новый чистый модуль по контракту `stats.py` / `measurements.py` / `pace.py`: числа и датаклассы на вход, фрозен-датакласс на выход, ни aiogram, ни сессий, ни русского текста.

**Расход за тренировку** — одна формула и одна таблица:

```
ккал/мин = MET × 3.5 × вес_кг / 200
```

MET («во сколько раз активность затратнее покоя») — справочные значения из Compendium of Physical Activities:

```python
MET_BY_EFFORT: dict[WorkoutType, dict[str, float]] = {
    "running":    {"easy": 8.3, "moderate": 9.8, "hard": 11.8},
    "swimming":   {"easy": 5.8, "moderate": 8.3, "hard": 10.0},
    "elliptical": {"easy": 5.0, "moderate": 7.0, "hard": 9.0},
    "gym":        {"easy": 3.5, "moderate": 5.0, "hard": 6.0},
    "home_workout": {"easy": 3.8, "moderate": 5.5, "hard": 7.0},
}
```

Ключи `effort` — существующие `EFFORT_VALUES` из `workout_types.py`. Если `effort` пропущен — берём `"moderate"` как дефолт; если нет `duration_min` или неизвестен вес — тренировка в сумму **не попадает** вовсе.

**Базовый обмен** — Миффлин-Сан Жеор: `10×вес + 6.25×рост − 5×возраст + 5` для мужчин, `−161` для женщин. Возраст — `periods.years_since(birth_date, ref)`.

**Дневной ориентир:**

1. BMR × 1.2 (бытовая активность) = расход без тренировок;
2. + средний дневной расход на тренировках за период (сумма по периоду / число дней);
3. − дефицит из цели: `target_rate_kg_per_month × 7700 / 30`, знак по `goal_type` (для `gain`/`muscle` это профицит, для `maintain` — ноль).

Результат — что-то вроде:

```python
@dataclass(frozen=True)
class EnergyStats:
    workout_kcal: int          # за период, по записанным тренировкам
    counted_workouts: int      # сколько тренировок вошло в сумму
    skipped_workouts: int      # сколько отброшено из-за пропущенных полей
    bmr: int
    daily_burn: int            # BMR × 1.2 + тренировки
    daily_target: int | None   # None, когда ориентир ниже порога (T-5)
    below_floor: bool
```

Константы (`1.2`, `7700`, порог) — именованные в этом же модуле, с комментарием откуда взялись.

### T-3 — Данные: расширить проекцию

`db/models.py`, `WorkoutStatRow` сейчас это «дата + тип», и `list_workouts_for_stats` в `db/workouts.py` выбирает ровно две колонки. Для расхода нужны `duration_min` и `effort`.

Расширить существующую проекцию (добавить два nullable-поля и две колонки в `select`), а не заводить второй запрос: единственный потребитель — `services/stats.py`, и он лишние поля просто игнорирует. Отчёт при этом остаётся на одном запросе к тренировкам.

Вес — `db_measurements.latest_weight(user_id)`, профиль — `db_profiles.get_profile(user_id)`; обе функции уже есть.

### T-4 — Врезка в отчёты

Как и в предыдущей задаче, всё в `services/reports.py`, потому что `/week`, `/month` и рассылка планировщика идут через `build_weekly_text` / `build_monthly_text`.

- в `_report_body()` (или рядом, если чище) дотянуть профиль и вес, собрать `EnergyStats`, положить в `ReportBody` полем `energy: EnergyStats | None`;
- `formatters/reports.py` — новый блок после тела отчёта; строки в `texts/reports.py`, числа через `fmt_number`.

Примерный вид блока (точные формулировки — на усмотрение, но без советов):

> Расход — около 2400 ккал в день, из них ~200 дают тренировки.
> Для −2 кг в месяц ориентир по питанию — около 1900 ккал в день.
> За неделю на тренировках ~1400 ккал (по 3 записанным тренировкам).

### T-5 — Безопасный порог и деградация

**Порог.** Если арифметика выдаёт ориентир ниже примерно уровня BMR, число не печатается вообще — вместо него строка «при таком темпе норма питания получается слишком низкой». Это не совет и не исключение из принципа «только факт»: это отказ выводить вредное число.

**Деградация — блок не показывается совсем**, если:

- нет пола, даты рождения или роста (все три шага онбординга скипаемые);
- нет ни одного замера веса;
- нет активной цели или в ней не задан `target_rate_kg_per_month` — тогда можно показать только расход (`daily_burn`, сумма за тренировки) без строки ориентира.

Отдельно стоит один раз мягко предложить дозаполнить профиль, если блок не показывается только из-за пустых полей. Это единственное «предложение», допустимое в задаче, и оно про данные, а не про поведение.

## Проверка

1. `uv run ruff check . && uv run ruff format .`
2. Миграции **не нужны** — схема не меняется (`duration_min` и `effort` в `workouts` уже есть). `uv run alembic revision --autogenerate -m drift-check` обязан выдать пустую миграцию; удалить её.
3. `uv run python -m momentum`, в боте:
   - добавить тренировку типа «зал» → спрашивается длительность и интенсивность, карточка их печатает;
   - добавить тренировку, пропустив оба поля → сохраняется, отчёт не падает, она не в сумме расхода;
   - `/week` с заполненным профилем, весом и целью с темпом → блок с расходом и ориентиром;
   - профиль без роста → блока нет, остальной отчёт цел;
   - цель без темпа → есть расход, нет строки ориентира;
   - агрессивный темп на малом весе → вместо числа строка про слишком низкую норму.
4. Сверить пару расчётов вручную: мужчина 35 лет, 180 см, 90 кг → BMR ≈ 1855, ×1.2 ≈ 2230; бег 40 мин moderate при 90 кг ≈ 620 ккал; при −2 кг/мес ориентир ≈ 1900 ккал/день.

Вне скоупа: калибровка ориентира по фактическому изменению веса, трекинг питания в любом виде, MET по темпу (мин/км) вместо кнопки усилия, отдельная команда-калькулятор, хранение калорий в БД, LLM-комментарий (см. `03-llm-report-graph.md`).
