# Тренерский комментарий к отчётам через граф LangGraph

## WHAT

> Добавить к недельным и месячным отчётам короткий тренерский комментарий от LLM, где **ветку разговора выбирает детерминированный граф**, а не модель. Факты считаются как сейчас (stats, measurements, pace, energy), триаж по наличию и объёму данных выбирает одну из ситуаций, у каждой ситуации свой узкий промпт. Числа в ответе проверяются против фактов; при ошибке или провале проверки отчёт уходит по текущему шаблону.

Делается **третьей**, после `01-goal-pace.md` и `02-energy-layer.md`: ветки `on_track` / `off_track` / `unsafe` опираются на `services/pace.py`, часть формулировок — на `services/energy.py`. Без них половина листьев графа недостижима.

## WHY

Цифры в отчёте уже есть, но без интерпретации их легко пролистать. Проблема в том, как обычно делают такой комментарий: отдают модели всё сразу и просят «написать разбор». Тогда акцент выбирает модель — и регулярно выбирает не тот: хвалит за неделю, в которой человек ни разу не взвесился, рассуждает о темпе, когда точек всего две, или выдумывает число, которого в данных нет.

Граф переворачивает ответственность: **о чём говорить, решает код, а модель только формулирует**. У каждой ситуации свой короткий промпт, и модель физически не может уехать не туда, потому что не видит ни контекста других веток, ни лишних данных.

Побочные выгоды, ради которых стоит именно граф, а не цепочка:

- самые частые ветки (пустая неделя, нет профиля, нет цели) **до модели не доходят вовсе** — ни токенов, ни задержки в последовательной рассылке;
- проверку «модель не выдумала чисел» с одной повторной попыткой и откатом на шаблон в графе выражает обычный условный переход, в линейной цепочке — нет;
- новая ситуация = новый лист + файл промпта, ничего существующего не трогается. Та же идея, что у генерик-FSM тренировок.

## Вердикт

Относится к боту: да.
Уже реализовано: нет. LLM, LangChain, LangGraph, `prompts/` в проекте отсутствуют (см. `pyproject.toml`, `config.py`).
Реализуемо: да, с оговорками — нужны новые зависимости, внешний API и ключ; broadcast становится медленнее на тех пользователях, чья ветка доходит до модели. Приемлемо при коротком таймауте и последовательной рассылке, которая уже есть.

## Принятые решения

- **LangGraph, не голый LangChain.** Проверено по `ecosystem-primer`: ветвление детерминированное, шагов несколько, агентного цикла с инструментами нет — это ровно профиль LangGraph.
- **Граф не ходит в БД.** Факты собираются снаружи, в `services/reports.py` (импурный слой, который уже этим занят), и подаются на вход как готовый снимок. Слои из CLAUDE.md остаются на месте, узлы графа — почти чистые.
- **LLM только в листьях.** Триаж, guard и сборка — обычные Python-функции.
- **Промпты — внешние `.md` файлы**, по одному на ветку, русские. Не строки в Python-модуле.
- **Кэш — своя таблица в БД**, а не персистенс LangGraph. Отчёт одноразовый, состояние между запусками не живёт, чекпойнтер не нужен.

## План

### T-1 — Зависимости, конфиг, наблюдаемость

`pyproject.toml`: `langgraph` + `langchain` + пакет провайдера. `config.py` / `Settings`: ключ API (`SecretStr`, пустой по умолчанию), имя модели, таймаут. Отдельный флаг `LLM_ENABLED` **не** вводить — пустой ключ и есть выключатель. Обновить `.env.example` и таблицу env в `README.md`.

Добавить переменные LangSmith (`LANGSMITH_API_KEY`, `LANGSMITH_TRACING`, `LANGSMITH_PROJECT`) — трейс показывает, какой веткой пошёл конкретный отчёт, а это главный вопрос при жалобе «бот написал ерунду».

Исполнитель обязан **подтвердить актуальные пакеты, версии, импорты и вызов модели** через скиллы LangChain/LangGraph и MCP «Docs by LangChain» — не писать интеграцию по памяти, библиотеки меняются быстро.

### T-2 — `services/llm/facts.py`: снимок фактов

Чистый модуль (без aiogram, без сессий, без LangGraph): из уже посчитанных `WeeklyStats` / `MonthlyStats`, `ReportBody` (с `pace` и `energy`) и опционального `UserProfile` собрать компактный сериализуемый `ReportFacts`.

Внутри — период, тотал и разбивка по типам, diff/pct, стрик или недельное среднее, тип цели и темп, статус темпа, дельта веса и ключевые обхваты, ориентир по калориям, плюс **флаги полноты данных** (есть ли цель, сколько взвешиваний в окне, есть ли свежий замер, есть ли профиль). Флаги — то, на чём работает триаж, поэтому их считать явно, а не выводить в роутере из вложенных `None`.

**Без** сырой истории тренировок по штукам: модель получает выводы, а не журнал.

### T-3 — `services/llm/graph.py`: граф

Состояние: `facts`, `route`, `comment`, `attempts`.

```
START
  │
  ▼
triage ──────────────────────────────────────────────┐
  ├─► no_data ─────────────────────────────► END (шаблон, без LLM)
  ├─► no_goal ────────────┐
  ├─► cold_start ─────────┤
  ├─► stale_measurements ─┤
  ├─► on_track ───────────┼─► guard ─► assemble ─► END
  ├─► off_track ──────────┤     │
  ├─► recomp ─────────────┤     └─(не прошёл)─► retry / fallback
  └─► unsafe ─────────────┘
```

`triage` — обычная функция, маршрутизация через `add_conditional_edges`:

| Ветка | Условие | Промпт про |
|---|---|---|
| `no_data` | ни тренировок, ни замеров | — (шаблон, LLM не зовём) |
| `no_goal` | тренировки есть, активной цели нет | только тренировочный ритм, ни слова о весе |
| `cold_start` | цель есть, истории < 2–3 недель | старт и привычка, **не** про темп — его ещё не из чего считать |
| `stale_measurements` | цель есть, свежих взвешиваний нет | почему без замеров разбор слепой |
| `on_track` | `pace.status` = `ahead` / `on_track` | что работает, что продолжать |
| `off_track` | `behind` / `stalled` | где разрыв, одно конкретное действие |
| `recomp` | вес стоит, талия падает | прогресс есть, весы его не видят |
| `unsafe` | `pace.status = "unsafe"` | притормозить |

Порядок проверок в триаже важен: сначала «данных нет», потом «данных мало», потом содержательные ветки. `unsafe` бьёт остальные.

Ветка `recomp` — главный приз всей затеи: это единственный вывод, который человек сам почти никогда не делает, и он целиком выводится из обхватов, которые мы уже собираем.

Узлы-листья — одна общая реализация, параметризованная ключом промпта; в графе они зарегистрированы отдельными именами, чтобы ветка была видна в трейсе.

### T-4 — Промпты

`src/momentum/prompts/report/<branch>.md` — по файлу на ветку. В каждом: роль, длина 2–4 предложения, тон поддерживающий, **только интерпретация переданных фактов** (не выдумывать числа и тренировки), без медицинских советов, без выхода за тему ветки.

Убедиться, что hatchling кладёт `prompts/**/*.md` в wheel (при необходимости `force-include` / package data), иначе в Docker файл не найдётся.

### T-5 — Guard и обработка ошибок

**Guard** — детерминированная проверка после генерации: все числа в ответе модели должны встречаться в фактах. Выдумала «сбросил 1.2 кг» при 0.4 в данных — не прошёл.

- не прошёл → условный переход обратно в тот же лист, **одна** повторная попытка (`attempts`);
- не прошёл второй раз → `fallback`, отчёт уходит по текущему шаблону.

Отдельно — `RetryPolicy(max_attempts=...)` на узлах с LLM: сетевые ошибки и рейт-лимиты это другой класс проблем и лечится другим механизмом. Любая необработанная ошибка, пустой ответ или таймаут → комментария нет, отчёт цел.

### T-6 — Склейка и кэш

Граф компилируется один раз на старте (не на каждый вызов), `invoke` — на пользователя внутри `build_weekly_text` / `build_monthly_text` в `services/reports.py`. `handlers/reports.py`, `scheduler.py` и админские вьюхи не трогаются — они уже зовут те же builders.

Заголовок секции комментария — константа в `texts/reports.py`; сборка HTML — тонкое расширение `formatters/reports.py`.

Кэш: таблица по `(user_id, kind, period_start)` с текстом комментария. Миграция через Alembic как обычно. Смысл — повторный `/week` в том же периоде не должен платить за модель заново.

Риск, который нельзя потерять: при включённом ключе каждый подписчик в `broadcast` ждёт LLM. Держать таймаут коротким и никогда не ронять рассылку из-за комментария.

## Проверка

1. `uv run ruff check . && uv run ruff format .`
2. `uv run alembic upgrade head`; повторный `--autogenerate` обязан дать пустую миграцию.
3. **С пустым ключом**: `/week` и `/month` работают ровно как до задачи, комментария нет, в логах ничего страшного.
4. **С ключом**, прогнать ветки на тестовых данных:
   - чистый пользователь без тренировок и замеров → `no_data`, модель не вызывается (проверить по трейсу в LangSmith или логу);
   - тренировки без цели → `no_goal`, про вес ни слова;
   - цель + два взвешивания → `cold_start`, про темп не рассуждает;
   - цель + месяц замеров, вес по плану → `on_track`;
   - вес стоит, талия уменьшилась → `recomp`;
   - агрессивное падение веса → `unsafe`.
5. Проверить guard: подменить ответ модели строкой с выдуманным числом → одна повторная попытка → откат на шаблон.
6. Проверить, что упавший или зависший API не ломает `broadcast`: отчёт уходит без комментария.

Вне скоупа: `/ask` и свободный диалог, недельные планы тренировок, парсинг свободного текста, агентный цикл с инструментами, доступ модели к сырой истории тренировок, генерация комментария заранее отдельным джобом, дробление `services/llm` на много модулей.
